# VPS → GX10 private Elova route (operator plan; not activated)

This is a **historical native-loopback frontend route proposal**, not the selected VPS frontend delivery. For the intended Docker-provider route and its own gateway approval gate see [vps-frontend-container.md](vps-frontend-container.md). It remains useful for GX10 private-route evidence; do not follow its VPS native frontend or loopback proxy steps for the Docker candidate. This is a future, separately authorized route procedure for the *current* main-line backend container topology, not a deployment script or evidence that a VPS is configured. This source change makes no host, proxy, Tailnet, firewall, DNS, TLS, Docker, credential, migration, or frontend change. Obtain explicit, exact-target authority for publication and frontend activation **after** reviewing this plan. Do not use the historical native backend service instructions in `native-services-runbook.md` to replace the running container backend.

## Fixed boundary and current evidence

Browser → VPS HTTPS reverse proxy → `127.0.0.1:43180` frontend/BFF → Tailnet → GX10 **backend** TCP/43181. Browser calls only same-origin `/api/v1/*`; `apps/frontend/src/server/bff-proxy.ts` maps that to `/v1/*`. The private, credential-free `ELOVA_BACKEND_URL` is server-only; no `NEXT_PUBLIC_` equivalent, browser-to-GX10 proxy rule, or database credential on VPS. `apps/frontend/package.json` and `ops/systemd/elova-frontend.service` pin the frontend to loopback. The systemd unit is a template, **not** evidence of installation. Backend session/authorization checks still apply; a private route does not replace them.

At preparation time on GX10, `elova-postgres-1` and `elova-backend-1` were running only on `elova_elova_db`, with **no published host ports** (Postgres healthy; backend has no Docker healthcheck). Host `127.0.0.1:43181` is owned by a separate synthetic-preview mock, **not** by Elova backend. Do not forward to, stop, restart, rebind, or send real credentials to that preview. The tracked *unactivated* `ops/container/compose.yaml` is different: its profiled backend joins `elova_db` and dedicated `elova_edge`, with a candidate host-IP port publication; do not infer it is running or apply it to the existing containers. No DB host port, `ai`/`core` network attachment, wildcard/public/LAN/IPv6 **host** bind for the backend, or generic relay is an acceptable shortcut (the container's own `0.0.0.0` listener is separate from host publication). The current GX10 Tailnet IPv4 is an observation, not a reserved destination or proof of a source ACL.

**Unresolved identity/evidence:** the preparation record does not identify an approved VPS SSH host/user, an independently verified host-key fingerprint or a VPS Tailnet device/principal. No actual VPS proxy, TLS, `43180` listener, installed unit, deployment path, ACL/grant, or GX10 source restriction can therefore be asserted. A known_hosts entry or a numbered Tailnet peer is not independent proof that a machine is the approved VPS. Until the owner supplies those records, do not SSH, scan a candidate, or make a live route change. Recheck all observations at the authorized window.

## Evidence gates before any publication (stop on failure)

1. Record approved VPS hostname/IP and SSH user/identity **from the operator**, plus independently authenticated SSH host-key fingerprint; compare before any connection, never accept on first use. On that verified VPS only, read-only inspect the existing HTTPS virtual host/certificate and proxy target, service/user/deployment ownership, and `ss -H -ltnp 'sport = :43180'` (including IPv6). Establish the actual VPS Tailnet node identity, approved source IPv4/IPv6, and effective route to GX10. Do not guess a proxy syntax, domain, certificate, host, or source from repository examples.
2. Reconfirm GX10 `tailscale0` destination, backend/DB container identity, image, labels, network and port mappings **without inspecting env/secrets**, and `ss -H -ltnp 'sport = :43181'` on all interfaces. Preserve the preview on loopback. Review the effective Docker forwarding/userland proxy, nftables/iptables/DOCKER-USER rules (including IPv6), host firewall, IP forwarding, and Tailnet ACL/grant for the **verified VPS principal alone** to the *specific* GX10 TCP/43181 destination. Tailnet addressing and a Docker host-IP bind are not source restrictions. Require explicit deny for other Tailnet peers, LAN, public interfaces, and IPv6 paths; confirm from authorized denied-source probes as well as the approved VPS, before letting a public browser reach the BFF. Check that no route to TCP/5432 or shared `core`/`ai` networks is introduced. Do not attach either container to those networks.
3. Approve a distinct Elova-only backend publication/cutover plan from the **running** no-port container to the reviewed candidate topology, including provenance, backup/restore, migration compatibility, exact image/project/volume, rollback and preview coexistence. Docker cannot add a port to a running container; a blind `compose up`, generic restart, or replacement of the existing backend is not this route task. If the existing backend cannot be preserved or a separately authorized cutover cannot be made safely, stop. Do not use the preview loopback port or switch to wildcard bind. Approval must include effective Docker/firewall IPv4+IPv6 denial and source-only ACL proof, not just `ELOVA_TAILNET_IP` validation.
4. Separately approve frontend artifact/version compatibility, service activation, VPS protected server-only environment, and existing HTTPS proxy change. `ops/env/frontend.env.example` has no deployed value; set `ELOVA_BACKEND_URL` only after verifying the *current* private GX10 origin and port 43181. Keep frontend bound to `127.0.0.1:43180`; proxy only to that loopback listener and preserve existing non-Elova proxy routes. Do not expose the frontend on a wildcard/LAN/IPv6 socket or proxy `/v1` straight to GX10. No real owner password or n8n key may touch the synthetic preview.

## Separately approved rollout and reversible checks

Before touching anything, record the exact Elova-only previous proxy configuration, service active state, frontend release/config, GX10 backend image/container/network/port state, and ACL/firewall state in protected operator records; identify a rollback owner and a maintenance window. Keep current backend, DB, preview and other proxy sites intact during this preparation. Only within a **new explicit activation decision**, apply the reviewed source-restricted GX10 route; verify the approved VPS can reach `GET /v1/health/ready` with HTTP 200, `X-Elova-Api-Version: 1`, and ready database/migrations. Verify denied Tailnet/LAN/public/IPv6 attempts cannot reach 43181/5432 before enabling browser traffic. Then install/activate only the reviewed frontend on the verified VPS and change only its HTTPS location to the loopback BFF. Check `43180` is exclusively loopback (IPv4 and IPv6), public TLS and same-origin `/api/v1/health/ready`, login and approved workspace behavior, absence of GX10 origin in browser network/responses, and continued denial of direct GX10/DB access. A local liveness result or a successful allow probe alone is insufficient. Stop on any proof gap; do not publish a failing route.

Rollback if any isolation, health, or application check fails: first remove only the new public Elova proxy path (restore its recorded prior state); revert only the Elova frontend configuration/release/service to its recorded prior state, leaving unrelated proxy sites alone. Withdraw only the new GX10 TCP/43181 allowance/publication under the **approved backend cutover plan**: ACL/firewall deny first, verify denied paths, then restore the recorded no-port backend topology if doing so requires a controlled Elova-only recreation. Do **not** tear down the database, run down-migrations, remove volumes/secrets, stop the preview, change shared networks, or assume an old backend image is compatible with forward migrations. If backend rollback cannot preserve data/service compatibility, keep it private and escalate for forward repair instead of blind recreation. Recheck the prior browser/proxy state, backend readiness through a safe private path, DB and preview continuity, and no exposed ports after rollback; record evidence without secret values.

See `container-runbook.md` for the candidate image/migration/recovery gates. None of these future steps is executed or authorized by this documentation PR.
