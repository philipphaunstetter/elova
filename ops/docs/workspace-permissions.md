# Workspace access in the backend-first SaaS slice

**Source contract, not a live deployment or enrollment instruction.** The separate global `owners.role` is `user` or singleton `super_admin`; `workspace_members.role` is independently `owner`, `admin`, `editor` or `viewer` for each `(workspace_id, owner_id)`. A creator is provenance (`workspaces.created_by`) and does not keep access after membership removal. The designated owner reference ensures at least one member with role `owner` at commit. A super administrator can access any workspace by global role without a fabricated membership, but must still explicitly select it and send the matching `x-elova-workspace-id` for every scoped request. Membership/role is refreshed on each scoped request; writes and secret retrieval check it again in SQL, and member/settings changes serialize on the workspace row. Unknown or unselected workspace access denies by default.

| API operation | Owner | Admin | Editor | Viewer | Super-admin |
| --- | --- | --- | --- | --- | --- |
| Login/logout/session and workspace list | own account and memberships | same | same | same | own account; list all workspaces |
| Create a workspace / select an accessible workspace | yes, first owner of new workspace | yes, first owner of new workspace | yes, first owner of new workspace | yes, first owner of new workspace | yes; select any explicitly |
| `GET /v1/providers` (summaries), `/v1/workflows`, `/v1/executions`, `/v1/dashboard/metrics` | yes | yes | sanitized/summary only | sanitized/summary only | yes |
| `POST /v1/providers`, `POST /v1/providers/{id}/sync` (uses server-side encrypted key) | yes | yes | no | no | yes |
| `PATCH /v1/workspaces/settings` (name only) | yes | yes | no | no | yes |
| `GET/POST /v1/workspaces/members`, `PATCH/DELETE /v1/workspaces/members/{userId}`, `POST /v1/workspaces/ownership/transfer` | yes | no | no | no | yes |

There is **no n8n workflow write/execute endpoint** in this slice. Editor can read sanitized evidence but cannot fetch a key, create/sync providers or mutate membership/settings; any future keyless workflow action needs its own separately reviewed route authorization. Admin may manage settings and provider connections, not members or ownership. Provider `owner_id` remains creator/audit metadata; the provider's `workspace_id` determines tenant identity for workflows, executions and sync state. Only existing users can be attached by exact canonical email; member add never creates an account, and listing members is restricted to owner/global admin. No signup, invite, email delivery, billing or custom permissions.

To add a second person, a separately authorized operator must provision their ordinary account from **that person's chosen password** via a protected local absolute 0400 non-symlink file (same reader as initial captain bootstrap). The packaged backend command is `node dist/src/provision-user.js` (or `npm run provision-user --workspace @elova/backend`) with `ELOVA_USER_EMAIL`, `ELOVA_USER_NAME`, `ELOVA_USER_PASSWORD_FILE` and the separately approved backend database configuration. Password text never goes in env/arguments/logs/repository; `ELOVA_USER_PASSWORD` is rejected. Do not run this command just because the source supports it. The operator must confirm exact identity via the approved channel, ensure only the person controls the password handoff, remove the handoff file promptly and inspect the identifier on an uncertain commit before retrying. The initial super administrator must exist before the ordinary-user command will create an account. The new user has no workspace until an owner/global super-admin explicitly attaches them or they create their own.

Before demoting/removing the **designated** owner, first grant another already-provisioned member role `owner` (if necessary), then explicitly transfer the designated-owner reference to that member. Only then demote/remove the prior designated owner. Concurrent member/transfer changes serialize on the workspace row; the deferred composite FK to an actual `owner` member independently rejects a commit with no designated owner. Other owner members may be demoted/removed while the designated owner remains. Removed users' selected sessions for that workspace are cleared; downgraded sessions remain selected but their privileges are rechecked on every request. In-flight provider sync begun before a downgrade is not automatically canceled; newly initiated secret access is denied after the committed downgrade.

`apps/backend/migrations/0001_postgres_authority.sql` is unchanged and may already be applied; `0002_workspaces.sql` remains an unpublished forward migration and only a separately authorized operator may apply it. A database with an already-applied 0002 checksum requires a separately reviewed forward repair, never rewriting history/resetting data. No real account, key, migration, CI run or production action is part of this source change.
