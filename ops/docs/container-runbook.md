# Elova private two-container candidate — review only

**Repository/CI delivery, not GX10 operation approval.** No image publication, host Compose operation, credential issuance, production backup/restore, migration, backend activation, native-service replacement, n8n/VPS/LiteLLM change or shared `core-postgres-1` action is authorized by this file. Every host action below is **unexecuted** and independently gated. Retain production data and `ops/bin/elova-package-native`, `ops/bin/elova-native-release`, `ops/systemd/*`, and the native runbook as historical cutover assets; they do not operate this stack. There is no automatic native fallback.

## Identity and provenance gate (operator/release owner, separate approval)

`ops/container/compose.yaml` defines exactly project `elova`, services `postgres` and profile-gated `backend`. `postgres` alone joins private internal `elova_db` and owns volume `elova_pg16_data`; it has **no published port**. The backend joins only `elova_db` and dedicated project `elova_edge`, not `ai`, and publishes only `${ELOVA_TAILNET_IP}:43181:43181/tcp`. It binds `0.0.0.0` **inside the container only**; the host-IP publication is independent and must be verified. The DB is reachable by backend on `postgres:5432`; container mode rejects other DNS, host/port overrides, roles and database names. Default native mode still rejects remote database URLs and wildcard binds. `pull_policy: never`, no production `build:`, and `restart: 'no'` prohibit routine pull/build/restart. `docker compose up` with no profile starts **only postgres**, never backend. No migration occurs at either service startup. Do not set `COMPOSE_PROFILES=activate` for routine operations.

The reviewed candidate recipe is `ops/container/Dockerfile.backend` + `.dockerignore` + root `package-lock.json` on a locked source commit. Its Node 22 multi-architecture digest (currently `sha256:43ac6c60b8f89723f746e8a92ce91abd5017e627ce1ddfe4238355d3a30b772c`) must be independently checked for **Linux ARM64**, toolchain and policy before a trusted build; the PG16 Alpine index digest (`sha256:721873c34ceb9f8d8fc265984940dc982404c105f19ad51be9fdc5970a6080ea`) likewise needs independent ARM64 manifest/config, version, PGDATA path and vulnerability review. These are pinned candidate inputs, **not** approval to fetch or deploy them. Builder uses `npm ci`; runtime copies only compiled `dist/src`, production workspace dependencies and ordered SQL, runs non-root UID/GID 10001 without image secrets and never executes a migration as an entrypoint. The disposable Linux ARM64 CI job builds/executes a local candidate, records lock/recipe hashes, image ID/platform and OCI save stream hash, then discards it. CI does not push/publish and a single CI build does **not** establish reproducibility; that is a current evidence gap. Before any release, record exact source commit, base and PG manifest digests/ARM64 platform, dependency lock hash, build parameters/toolchain, SBOM and scan results, final artifact SHA/image ID or registry manifest digest, and compare two controlled builds or document the reproducibility gap. Independently verify approved private transfer signature/checksum and loaded image ID/config on target under **separate** host authority; no mutable tag resolution, implicit pull or registry push. `ELOVA_BACKEND_IMAGE` is the verified immutable `name@sha256:<64 hex>` or locally verified `sha256:<image ID>`; never substitute an unchecked tag. `ops/container/check-inputs.py` checks syntax offline, **not** trust or host suitability.

## Operator prerequisites before any host operation (all unexecuted)

Separately approve exact project/volume/network names and collision checks, current Tailnet IPv4 (historical `100.121.218.27` is not a reservation), host port availability, current platform/image identities, effective Docker resource limits and disk/WAL/backup/restore capacity with independent monitoring/quota policy. A named Docker volume alone is not a quota. Inspect the *actual* Docker IP-bound forwarding/userland proxy, IPv6, firewall/DOCKER-USER/nftables behavior and source-specific Tailnet ACL/grant for the approved frontend/VPS principal; test denied access from unauthorized Tailnet, LAN, public interfaces. Host-IP publication is not an ACL; Docker bridge membership is not an administrator-proof boundary. If publication leaks or cannot be constrained, **stop**, do not switch to wildcard host bind or join `ai`. Restrict who can attach to project bridges and verify no cross-network route. Frontend remains the existing server-side `/api/v1/*` BFF with same-origin browser requests and a private, credential-free Tailnet `ELOVA_BACKEND_URL` on 43181; no frontend/VPS update is part of this delivery. Backend auth, owner-scoped tenancy and pre-persistence sanitization remain mandatory; network trust does not bypass them. Future LiteLLM/`ai` integration and credentials require separate approval; neither service joins `ai` now.

Generate **new** protected Elova-only files in a separately authorized credential process, never in this repository, CI settings, shell history, image, build args or logs. `postgres_admin` is an independently escrowed DBA password, readable only by the verified PostgreSQL image UID (candidate Alpine UID 70; verify actual image); `postgres_app` is an independent random **alphanumeric at least 32-character** login password for `elova_backend`, also readable only by that UID. `database_url` contains the same app password URL-encoded in `postgresql://elova_backend:<password>@postgres:5432/elova_vnext`; do not print it or interpolate it in Compose. `session_key` and `credential_key` are two **distinct independently random canonical base64-encoded 32-byte** application keys. The latter three mounts must be owned by backend UID 10001 with mode 0400, or root with group 10001 and mode 0440; never world-readable, symlinks or writable by the runtime. All five files live under the protected absolute Elova-only `ELOVA_SECRETS_DIR`, backed by independently reviewed storage/permissions and escrow. The PostgreSQL admin credential and app role are separate. The one-off migrator currently uses the same app DB role and both app keys because `loadConfig` is shared; no least-privilege role split is claimed. Loss of either app key can affect old sessions/encrypted credentials; a database dump alone does not restore service.

The official fresh-volume PG entrypoint (`POSTGRES_PASSWORD_FILE`, SCRAM host authentication, peer local authentication) invokes `ops/container/init-elova-db.sh` **only at new-cluster initialization**. That script creates a non-superuser app login and app-owned `elova` schema; the role's database-specific search path selects it for migrations and runtime. It is **not** a migration, owner bootstrap or safe way to repair an existing cluster. Validate exact PG image/entrypoint and empty volume before provisioning; never attach existing/shared PGDATA or use `core-postgres-1`. If a volume or schema has unknown contents, stop for DBA disposition. Postgres health via `pg_isready` alone does not establish authentication, migration or restore health. No DB host port, default/external/`ai` network, third always-on service, frontend container or shared storage is configured.

## Separately authorized sequence (example invocation shape, NOT performed)

After the checks above, only an approved Docker operator may set `ELOVA_SECRETS_DIR`, `ELOVA_BACKEND_IMAGE` and `ELOVA_TAILNET_IP`, run the offline syntax check and review `docker compose -f ops/container/compose.yaml config` **without printing secret values** (the template contains paths, not values). Bring up **postgres only** with `docker compose -f ops/container/compose.yaml up -d postgres` on a verified fresh project/volume. Check exact project identity, PG16 major, SCRAM, app role `current_user`, `current_schema() = elova`, dedicated volume and network memberships, and absence of any DB host port. Do not use unqualified `up --profile activate` or `COMPOSE_PROFILES` as a convenience.

Only after an independent migration decision, run the deliberate one-off job from the **same checked backend image**, with no dependency startup and **no published ports**: `docker compose -f ops/container/compose.yaml run --rm --no-deps --no-TTY --no-ports backend node dist/src/migrate.js`. The profiled backend service is targeted as a transient job, not started as an API. It inherits two networks but has no host publication; review that egress before use. Verify `schema_migrations` contains exactly the ordered `0001_postgres_authority.sql` name and SHA-256 checksum from the approved image/source, the expected schema/role and readiness **after** migration; job exit code alone is insufficient. Migrations are forward-only; failure/uncertain commit means stop and preserve evidence, with DBA-approved forward repair, never blind retry/drop/down migration. No owner or n8n sync is bootstrapped here.

**Before backend activation**, the recovery custodian must make a consistent Elova-only PG16 backup after the initial migration, hash/encrypt it, record protected retention, independent failure-domain copy, access/incident owner and independent key escrow. Retain roles/grants/SCRAM setup, Compose spec, exact PG and backend image artifacts/digests, URL/key custody and migration metadata in recovery inventory. Separately approve a *new disposable isolated PG16 restore target* with its own private network/volume and **no** host port, backend, `ai` or shared mount. Reconstitute role/config/key identities under recovery custody, restore without ever overwriting a live volume, and verify startup, migration name/checksum, schema and metadata-only connectivity. Record timestamp, owner and result; do not activate on missing/failed backup or restore proof. Scratch cleanup requires separate exact-target approval and hold check, not `volume prune` or generic project cleanup; preserve backup for retention.

Only a distinct later activation decision can allow `docker compose -f ops/container/compose.yaml --profile activate up -d --no-deps backend`, after backup/restore and network gates. Confirm backend listener only on the *current* Tailnet host IP:43181, forbidden interfaces denied, approved ACL, `/v1/health/ready` returns HTTP 200 with `checks.database=ready`, `checks.migrations=ready`, and `X-Elova-Api-Version: 1`; verify existing BFF private same-origin flow without editing the VPS. `/live` and PG health alone are insufficient. Keep unattended restart/host-boot policy a separate decision. On failed activation, stop only the Elova backend; retain DB, backup, secrets and evidence. A previous image is not automatically compatible with later forward migrations even if counts match; require checksum/readiness and release review. No down-migration, drop, secret destruction/rotation, shared-cluster fallback or native-helper activation without separate exact-target authority.
